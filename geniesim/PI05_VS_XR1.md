# π0.5 vs XR-1：Genie Sim 实现逐项对比

目的：XR-1 在 Genie Sim instruction 套件上做 SFT 前，把它和 π0.5 基线的实现**逐项对齐或说明差异**，
找出会静默影响结果的细节，并给出训练决策需要的数据。

- π0.5：`Anonymous-694/ACoT-VLA@agibot_world_challenge`(`9ded4eb`)，
  配置 `pi05_genie_sim_instruction_and_robust_20260526`(`src/openpi/training/config.py:2149`)
- XR-1：本仓库(上游 `0dd7aef` + `geniesim/` 下的改动)
- 评测侧：genie_sim 2026-07-30 版本(`source/geniesim_benchmark`)
- 所有数字均为实测或直接读代码得到；推测会明确标出

| | π0.5(H=50) | XR-1(H=30) |

### 1.5 归一化

| | π0.5 | XR-1 |
| --- | --- | --- |
| 状态 | 分位数归一到 [-1,1](q01/q99)，**不裁剪**，然后离散成 256 档写进文本 | 分位数归一到 [-1,1]，**裁剪到 [-1,1]**，连续值进投影层 |

## 2. 输入

### 2.1 图像

| | π0.5 | XR-1 |
| --- | --- | --- |
| 相机 | head + 左右腕(同样的三路) | 同 |
| 缩放 | `resize_with_pad` 到 **224×224**(保持比例，补黑边) | `resize_image(factor=32, max_pixels=160000)`：**不补边**，各边取整到 32 的倍数 |
| head 640×400 | 有效内容 224×140 = 3.1 万像素 | 480×288 = **13.8 万像素**(比例从 1.60 拉成 1.67) |
| 腕 1280×1056 | 有效内容 224×185 = 4.1 万像素 | 416×352 = **14.6 万像素**(1.212 拉成 1.182) |
| 视觉 token | 每张 256，三张共 **768**(含黑边) | 135 + 143 + 143 = **421** |
| 每样本总 token | **固定 968**(768 + 文本 200，补齐)+ 50 个动作 | **521–559**(不补齐，拼接) |
| 增强 | head：随机裁 95% + 缩放回原尺寸 + 旋转 ±5° + 颜色抖动；腕：只做颜色抖动 | 三路都只做颜色抖动(亮度/对比度/饱和度各 50% 概率，三张图参数相同)；**不裁剪、不旋转** |

两点影响：

- XR-1 每张图的像素多 3–4 倍，token 却更少，因为 Qwen3-VL 每个 token 覆盖 32×32 像素(patch 16 加 2×2 合并)。
  小目标(数字、颜色块、台球)的可见度上 XR-1 应该占优，这一点是推测。
- XR-1 不做几何增强，对相机位姿扰动的鲁棒性可能弱于 π0.5，这一点对 **robust 榜**有影响(也是推测)。
  如果 robust 分数明显低于 instruction，可以优先试加随机裁剪。

拉伸比例在训练和推理两侧用的是同一个 `resize_image`，所以一致，不算 bug。

### 2.2 状态

| | π0.5 | XR-1 |
| --- | --- | --- |
| 内容 | 14 关节 + 2 夹爪，补零到 32 维 | 14 关节 + 2 夹爪，放进 60 维的固定槽位 |
| 进入方式 | 离散成文本 token 放进 VLM 前缀 | 两路：①训练时 VLM 里的 `<state>` token(只服务辅助 loss)；②动作专家 DiT 的 state 投影 |
| 精度 | 256 档，约 0.012 rad/档(按 3 rad 的区间算) | 连续值 |
| EEF 位姿 | 不进模型 | **不进模型**；只在推理侧用来把增量还原成绝对位姿 |

### 2.3 推理时 VLM 看到什么(XR-1 特有，已核对)

训练时的序列是"图像+指令 → `Robot state: <state>` → `<a_0>…<a_29><score>`"，
但 DiT 只取到 `<state>` 那一轮**之前**的 KV cache(`action_vlm_condition_segments`)。
推理客户端只发"图像+指令"那一轮。所以 **DiT 的条件在训练和推理两侧完全一致**。
`<a_i>` 和 `<score>` 只用于训练时的辅助 loss(§4.3)。

## 3. 动作表示

| | π0.5 | XR-1 |
| --- | --- | --- |
| 手臂 | **关节**增量：`a_t − q_now`(14 维) | **末端**增量，用当前末端自身坐标系表达：位置 `Rᵀ(p_t − p)`，姿态 `rotm2aa(Rᵀ R_t)` |
| 夹爪 | **绝对值** | **增量** `g_t − g_now` |
| 腰 / 底盘 | 不输出(instruction 配置) | 输出 1+3 维，数据里全为 0；loss 里也监督它们(对应的 std 是 0，归一化后恒为 0) |
| horizon | 50 步(1.67 s) | 30 步(1.0 s) |
| 推理还原 | `AbsoluteActions`：加回当前关节 | `recover_action`：用当前 EEF 位姿和夹爪还原 |
| 发给仿真 | `JOINT_ABS`，直接执行 | 服务端解 IK 后发 `JOINT_ABS`(仿真自带 IK 不够准，§8 S4)；可选 `EEF_ABS` + `base_link: arm_base_link` |

需要注意的影响：

- **夹爪是增量，和常见的"夹爪用绝对值"做法相反。** 数据侧没有问题：增量的基准是当前夹爪状态，
  还原时加回同一个状态，往返验证误差 < 1e-7。风险在评测侧：评测下发的 `gripper_states`
  经过 `label_state_crsb`(乘以 −1)后，必须和数据集 `state[0:2]` 的范围(约 [-0.785, 0])一致，
  否则还原出来的夹爪目标会整体偏移。G2_omnipicker 的配置正好是乘 −1 / 除以 −1，
  π0.5 依赖的是同一套映射，所以**大概率没问题，但第一次评测必须打印出来核对**(§8 S5)。
- **EEF 动作要多做一次 IK**。仿真自带的 IK 每步用"当前实测关节"作种子、只迭代 3 次，
  实测误差偏大，所以改在服务端解(§8 S4)。π0.5 发的是关节目标，没有这一步。

## 4. 模型与训练目标

### 4.1 结构

| | π0.5 | XR-1 |
| --- | --- | --- |
| VLM | PaliGemma(Gemma 2B + SigLIP) | Qwen3-VL-4B |
| 动作专家 | Gemma 300M，adaRMSNorm 注入时间步 | 36 层、1024 维 DiT，adaLN 注入时间步；逐层 attend VLM 的 KV cache |
| 总参数 | 约 3.3B | 约 5B |
| 训练范围 | 全参(没设 `freeze_filter`) | 全参，只冻结词嵌入；视觉塔和 LLM 的 MLP 开梯度检查点 |
| 框架 | JAX，FSDP=1(纯数据并行) | PyTorch Lightning + DeepSpeed ZeRO-2(Lightning 默认) |

### 4.2 Flow matching

| | π0.5 | XR-1 |
| --- | --- | --- |
| 时间步分布 | Beta(1.5, 1)，偏向噪声端 | 同样是 Beta(1.5, 1) 的变换(1−t 约定)，偏向噪声端，**等价** |
| 每个样本采几个时间步 | 1 | **4**(`training_repeat=4`，VLM 前向复用一次，只重复 DiT) |
| 推理积分步数 | **10** 步 Euler | **5** 步 Euler |
| loss | MSE(在 32 维上平均，16 维是补零) | 0.5·MSE + 1.0·频域 L1(FFT，排除底盘维) + 0.5·VLM 多候选 L1 + 0.5·打分 |

### 4.3 XR-1 的辅助 loss

VLM 在 `<a_i>` 位置为每一步预测 5 组候选动作，只取误差最小的那组算 L1(winner-take-all)，
`<score>` 再去回归各组候选的误差。这一路**只在训练时有**，推理不用；作用相当于让 VLM 表征里带上动作信息。
π0.5 没有对应的东西。

### 4.4 async_train(XR-1 特有，官方默认开)

训练时有 50% 的 batch 随机取 1–6 步真值动作作为"前缀"，只在剩余步上算 loss，
同时用一次完整的 5 步生成来算样本权重(`|生成结果 − 真值|`，裁剪到 [0.5, 5])。
它服务于**异步推理**：机器人执行上一段动作的同时预测下一段，已经要执行的那几步作为前缀传进去。

Genie Sim 是**同步**的：`act()` 在动作缓冲区清空后才发推理请求，仿真等结果回来再继续，
推理延迟不会造成动作缺口。所以：

- 开着：一半训练量花在推理时用不到的"带前缀"模式上，而且每个这样的 batch 要多跑 5 次 DiT 生成
- 关掉(`model.params.model.async_train=false`，README 里给出的选项)：训练模式和推理一致，速度见 §7

预训练权重本身是开着 async 训出来的，关掉它属于对后训练配方的改动，不过这是官方支持的开关。

### 4.5 training_repeat=4 的计算量

VLM 对每个样本只算一次，动作专家在它的 KV cache 上做 4 道去噪题：同一个真值动作，4 组不同的噪声和时间步
(`XR1._repeat` 在 batch 维 `repeat_interleave`)。π0.5 每个样本只做 1 道。

| 部分(每样本一次前向，估算) | 参数 | token | 计算量 |
| --- | ---: | ---: | ---: |
| VLM 语言模型 | ~4B | ~535 | ~4.3 TFLOP |
| DiT × 1 | ~0.6B | 32(sink + state + 30 动作) | ~0.04 TFLOP |
| DiT × 4 | | | ~0.16 TFLOP |

多出来的 3 次只占总量约 **3–4%**(不含视觉塔，没单独实测)。async_train 每次要多跑完整的 5 步生成，
所以它的开销(11%，实测)明显大于 training_repeat。遍历次数不受影响，每个 epoch 里的去噪监督是 π0.5 的 4 倍。

### 4.6 batch 怎么组：拼接 vs 补齐

| | π0.5 | XR-1 |
| --- | --- | --- |
| 方式 | 每个样本补齐到固定长度(968 + 50)，叠成 `[B, L]` | 每张卡的 32 个样本**首尾拼成一条**约 1.7 万 token 的序列(`custom_collate.py`) |
| 样本隔离 | padding mask | `cu_seq_lens` + flash-attn 变长注意力，每段只看自己；位置编码每段从 0 开始；`_unpad` 再按段切回给 DiT |
| 超长 | 只截断文本 | 超过 `MAX_LENGTH`(20,000)的样本**静默丢掉** |

两者在数学上等价，都是 32 个相互独立的样本，XR-1 只是省掉了 padding 的计算。**对遍历次数没有影响**：
每步每卡仍然是 32 个样本，30k × 256 ÷ 589,795 = 13.0 epoch。唯一的例外是超长丢样本，实测最长 17,888，不会触发；
训练时 wandb 的 `train/token`(每步拼接后的长度)可以用来盯这一点。
动作 loss 对所有有效动作元素取平均，每个样本都是 30 步，所以样本权重相等，不会因为图像 token 多而偏向某些样本。

### 4.7 分布式：DeepSpeed ZeRO-2 vs JAX 数据并行

| | π0.5(openpi，JAX) | XR-1(PyTorch Lightning) |
| --- | --- | --- |
| 框架 | JAX；`fsdp_devices=1` = **纯数据并行**，每卡一份完整模型和优化器状态 | DeepSpeed **ZeRO-2**(Lightning 默认)：优化器状态和梯度按 8 卡切分 |
| 能不能用 DeepSpeed | 不能，DeepSpeed 只支持 PyTorch | — |
| 每卡常驻显存(估算) | 3.3B：参数 + AdamW + EMA ≈ 65 GB，在 80 GB 卡上放得下 | 5B：bf16 权重 10 GB(每卡全量) + fp32 主权重和 Adam 60 GB ÷ 8 = 7.5 GB + 梯度约 1.3 GB |
| 不切分会怎样 | — | 前三项约 80 GB，96 GB 的卡放不下每卡 32 的激活 |
| checkpoint | 只存参数(发布版 12 GB) | 连同 8 份优化器分片一起存，**64 GB/个** |

## 5. 训练超参

| | π0.5 | XR-1 官方默认 | XR-1 本次 |
| --- | --- | --- | --- |
| 全局 batch | 256(所有卡平分，openpi 没有梯度累积) | 48(单卡 demo) | **256 = 8×32，不累积** |
| 步数 | 50k | 10k | **30k** |
| 训练帧 / epoch | 589,795 | — | 589,795 |
| 等效 epoch | **21.7** | — | 13.0 |
| 峰值学习率 | 5e-5 | 2e-5 | 2e-5 |
| warmup | 10k 步(20%) | 500 步 | 500 步 |
| 之后 | **恒定**(`decay_lr == peak_lr`) | cosine 降到 5e-6 | 同官方 |
| 优化器 | AdamW β(0.9, 0.95)，wd 1e-10(相当于 0) | FusedAdam β(0.9, 0.95)，wd 0.1(bias/norm/adaln 不衰减) | 同官方 |
| 梯度裁剪 | 1.0 | 1.0 | 1.0 |
| EMA | **0.999** | 无 | 无 |
| 精度 | bf16 | bf16-mixed | bf16-mixed |
| 存 checkpoint | 每 5k | 每 10k | 每 10k |

学习率为什么不照搬：5e-5 恒定加 EMA 是 openpi 给自己的模型配的，权重在 EMA 下被平滑。
XR-1 没有 EMA，直接用 5e-5 全参训一个 4B 的 VLM，风险更大。它自带的 2e-5 + cosine 是唯一和这个模型绑定的配方。
如果想试，更稳妥的是另开一组 5e-5 的对照，而不是替换掉默认值。

### 5.2 各实现遍历了多少遍数据

样本数 = 全局 batch × 步数；epoch = 样本数 ÷ 参与采样的帧数。

| 实现 | 全局 batch | 步数 | 样本数 | 参与采样的帧数 | epoch |
| --- | ---: | ---: | ---: | ---: | ---: |
| π0.5(官方配置) | 256 | 50k(发布模型的实际步数查不到) | 12.8M | 589,795(子任务段，含 reset 截断) | **21.7** |
| XR-0(官方 `config.py`) | 16×卡数(没写) | 30k | 8 卡时 3.84M | 不详(新版全量 73.9 万) | 8 卡时约 5–6.5 |
| XR-1 本次(30k) | 256 | 30k | 7.68M | 589,795 | **13.0** |
| XR-1 若用 20k / 50k | 256 | 20k / 50k | 5.12M / 12.8M | 589,795 | 8.7 / 21.7 |

XR-1 一个 epoch = 589,795 ÷ 256 ≈ 2,304 步，关掉 async 约 4.1 小时。

## 6. 推理与评测侧

### 6.1 协议和输出

| | π0.5 | XR-1(`xr1_policy.py`) |
| --- | --- | --- |
| 入口 | `tunnel_agent.py`：解 JPEG → openpi policy | 解 JPEG → XR-1 客户端的同一套预处理 → 本地模型 |
| 输出 | `JOINT_ABS`，50 步 | 服务端 IK 后 `JOINT_ABS`，30 步(可选 `EEF_ABS`) |
| 平滑 | **两条路径都没有**：`filter_abs_joint()` 第一行就 `return action`，`smooth_alpha` 是死代码 | 同左 |
| IK | 无 | 默认在服务端解(LM，精确 FK)，发 JOINT_ABS；仿真自带的 3 次迭代 IK 误差太大(§8 S4) |

### 6.2 图像链路

评测下发的是 JPEG(网关编码)，训练用的是 HEVC 视频帧，两种压缩伪影不同。π0.5 也一样，属于两边共有的差异。
XR-1 推理侧必须用和训练同一个 `resize_image`，不能 letterbox，也不能沿用别的模型的预处理。

### 6.3 每次推理执行几步(D5)

仿真会**把返回的所有步都执行完**(`action_buffer` 清空才再推理)。

| | 每次推理覆盖 | 每个 episode 的推理次数(相对值) |
| --- | --- | --- |
| π0.5 | 50 步 = 1.67 s | 1× |
| XR-1 发 30 步 | 1.0 s | ~1.7× |
| XR-1 发 16 步(RoboCasa365 官方评测用的就是 16) | 0.53 s | ~3.1× |

远程评测每次推理都要传一次三路图像，网络传输占了大头，推理次数直接决定评测耗时。
本次发 30 步，耗时和 π0.5 接近；需要更多闭环修正时可以试 16 步。

## 7. 训练速度与加速

**实测**(8×H20，每卡 32，30 步，去掉前 5 步；tqdm 只有整秒精度，所以用均值估算总时长)：

| 配置 | s/step | 50k 步需要 | 显存峰值 |
| --- | ---: | ---: | ---: |
| async_train 开(官方默认) | 7.20(中位数 7) | 100 h ≈ **4.2 天**(30k：2.5 天) | 95.7 GB |
| async_train 关 | 6.44(中位数 6) | 89 h ≈ **3.7 天**(30k：2.2 天) | 95.2 GB |

关掉 async 快约 **11%**，因为带前缀的 batch 不用再多跑一次 5 步生成；显存基本不变，余量都只有约 2.5 GB。之前冒烟测试报的 8.6 s/step 把前几步也算进去了，偏高。

其他观测：

- 训练过程中 GPU 利用率持续在 ~100%，数据加载**不是瓶颈**：单进程每样本 260 ms，每卡 8 个 worker，
  算下来每步约 1 s 的数据准备时间，被约 7 s 的计算完全掩盖
- 每样本 token 是 521–559，32 个拼起来最多 17,888，没有碰到 `MAX_LENGTH`(20,000)，所以没有样本被丢

加速选项，按"收益/风险"排序：

| 选项 | 预期收益 | 代价 / 风险 |
| --- | --- | --- |
| 关 async_train | 见上表 | §4.4 |
| 中间 checkpoint 删掉优化器分片 | 每个从 64 GB 降到约 10 GB；50k/5k 存 10 个时，全量是 640 GB | Lightning 的 DeepSpeed 策略**忽略** `save_weights_only`，总是连优化器一起存；只能事后删 `zero_pp_rank_*_optim_states.pt`，保留 `mp_rank_00_model_states.pt`(`deploy.py` 只读它)。中间点不能续训，保留一个全量的 `last.ckpt` 即可 |
| 降低 `max_pixels` | token 数和时间大致按图像 token 下降 | 偏离预训练的分辨率设定；小目标可见度下降。**不建议** |
| 视频转成目标分辨率 + 短 GOP | 加载更快 | 加载本来就不是瓶颈，**不需要** |
| 关梯度检查点 | 少一次重算 | 每卡 32 时显存只剩 1.2 GB，**不可行** |
